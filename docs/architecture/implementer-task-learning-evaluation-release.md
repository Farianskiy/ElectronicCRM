# Этап 5. Единая сравнительная оценка и управляемый выпуск правил

Реализовать непосредственно в проекте. Сохранить предыдущие этапы: самостоятельную фоновую обработку, общее распознавание, жизненный цикл подтверждений, происхождение знаний и исключение источника. Не ограничиваться аудитом, планом или предварительным набором тестов.

## Пользовательский результат

Для области «производитель + тип товара» пользователь выбирает подготовленную неизменяемую RuleSetVersion, запускает сравнение с действующей конфигурацией и получает один отчёт: что исправлено, что ухудшено, какие данные проверены, можно ли включить версию и что мешает. Включение остаётся явным действием с причиной и выполняется через существующий RuleSetSwitcher. Следующий запуск импорта и preview использует включённую версию.

Замыкаемый участок цикла:

подтверждения → подготовленные черновики → версия-кандидат → сравнение с текущей конфигурацией → проверка готовности → явное включение → последующее распознавание.

Этап касается выпуска RuleSetVersion всех трёх существующих видов правил. Одобрение словарных предложений остаётся отдельным действием с EvidenceRevision из этапа 4. Не объявлять его объединённым с выпуском правил и не вводить незаметное автоматическое обучение или включение.

## 1. Использовать существующие механизмы

Опорные компоненты: CatalogEffectiveRecognitionService, CatalogRecognitionRunContext, RuleSetVersion/Entry, RuleSetReport, RuleSetBatchPreviewService, RuleSetTrainingCheckService, RuleSetActivationValidator, RuleSetSwitcher, RecognitionMutationGate, TrainingSampleReader, LearningProvenanceService.

Расширить существующий отчёт и проверку активации; не создавать второй механизм активных версий, параллельную историю выпусков, универсальный workflow, отдельную очередь или микросервис. Допустимы необходимые аддитивные поля и версионированный ограниченный JSON-снимок существующего отчёта. Если действующие ограничения модели мешают, сначала найти минимальное совместимое расширение; не переписывать старую историю.

Текущие проверки пакета, владельца, версии пакета, состава строк, конфликтов, наличия предложений, состояния учебных оснований и expected sequence сохраняются. Новая сравнительная оценка добавляется к ним, а не заменяет их. В этом этапе выпуск по-прежнему использует доступный пользователю пакет импорта. Отдельный выпуск без пакета не добавлять.

## 2. Сравнивать реальное распознавание

На одних входах выполнить две конфигурации:

- текущая: baseline + действующая версия области, либо baseline при отсутствии активной версии;
- предлагаемая: тот же baseline + выбранная версия-кандидат вместо действующей.

Использовать общую реализацию распознавания, нормализации значений, объединения результатов и обнаружения конфликтов. Не собирать отдельный упрощённый recognizer для отчёта. Явный выбор версии для оценки не должен менять активную версию в БД или загрязнять кеши обычного импорта/preview. Нельзя объединять правила кандидата поверх действующей версии.

Принимать только полную область. Ошибка исполнения, повреждённые правила и timeout — ошибки оценки, а не успешное отсутствие совпадения. Ручные значения импортированных товаров не перезаписывать. Для оценки распознавания входом служат имя и область, а не готовые ручные значения строки.

## 3. Зафиксировать входы и конфигурации

Отчёт хранит неизменяемый снимок:

- область, автор, время, версия формата и исполнителя;
- ID и состав версии-кандидата, ID действующей версии либо отсутствие версии, sequence области;
- фактические baseline-зависимости обеих сторон: словарные термины, профили и определения характеристик, влияющие на результат, включая необходимые значения/содержимое;
- состав проверяемых входов, ожидаемые значения и исходные ExampleId/FeedbackId;
- результаты обеих сторон, знаменатели и значения метрик, применённую политику допуска и причины решения.

Одних ID изменяемых профилей или времени запуска недостаточно для воспроизводимости. Хранить необходимые данные и стабильные отпечатки канонического представления: порядок строк, свойства JSON и представление чисел не должны случайно менять отпечаток. Не копировать посторонние области или весь справочник без необходимости.

Построение снимка должно видеть согласованное состояние БД. Не держать общий mutation gate на всё время расчёта. Оценка может закончиться после изменения данных, но такой отчёт остаётся историческим и не даёт права включения без проверки актуальности.

Обеспечить повтор вычисления по сохранённому снимку поддерживаемого формата без обращения к изменившимся живым данным. Исключённые впоследствии источники допустимы только для воспроизведения старого отчёта с явной исторической отметкой; они запрещены в новой оценке и новом допуске к выпуску. Старый отчёт при повторе не перезаписывать. Неподдерживаемый исполнитель/формат должен возвращать явную причину невозможности воспроизведения.

## 4. Разделить проверку оснований и контроль качества

Учебные основания черновиков проверять существующим TrainingCheck. Не называть успешный recheck независимой оценкой качества.

Контрольную выборку строить из доступных текущему пользователю активных явных TrainingExamples нужной области с доступным и не исключённым Feedback. Соблюдать действующие права на разметку; глобальный sample reader не должен раскрывать чужие значения через новый отчёт.

Единица оценки — нормализованное имя + характеристика в фиксированной области. Одинаковые подтверждения этой единицы учитываются один раз. Разные ожидаемые значения для одной единицы — конфликт разметки: показать его и запретить готовность отчёта, не выбирать большинство и не выбрасывать конфликт молча.

В отдельную группу отнести имена, присутствующие в сохранённом evidence черновиков кандидата или действующей версии. Проверять все три вида evidence, в том числе checked, а не только supporting; искать пересечение по нормализованному имени внутри области, а не только по ExampleId. Все характеристики одного такого имени исключаются из контрольной группы. Счётчики исходных записей, дублей, конфликтов, пересечений и оставшегося контроля видны в отчёте.

Группу без известных пересечений обозначать «Контроль без пересечения с основаниями правил». Не утверждать полную статистическую независимость: происхождение всех исторических baseline-терминов может быть неизвестно. Эту границу показывать в описании отчёта.

Если контроля недостаточно, вернуть понятное состояние «Недостаточно контрольных примеров», объяснить, какие примеры нужны, и дать переход к существующему подтверждению примеров. Не дополнять контроль обучающими именами и не создавать фиктивную метрику качества. Не добавлять отдельный редактор эталонных датасетов в этом этапе.

## 5. Метрики с явными знаменателями

Для каждой размеченной единицы классифицировать результат каждой стороны: правильное значение, неправильное значение, отсутствие значения, конфликт распознавания. Не оценивать неразмеченные характеристики как ошибочные либо правильные. Использовать общую доменную нормализацию.

Показать количества и доли по общей выборке и характеристикам:

- правильные / все оцениваемые единицы;
- неправильные, пропуски и конфликты с тем же явно указанным знаменателем;
- исправления: раньше не было правильного результата, теперь есть;
- регрессии: раньше было правильное значение, теперь неправильное, пропуск или конфликт;
- построчные различия двух сторон с причиной и исходными ID.

При нулевом знаменателе доля отсутствует, а не равна 0% или 100%. Число найденных предложений в пакете и покрытие совпадениями не называть точностью. Метрики контрольной группы отделить от диагностических показателей пересекающихся учебных имён и операционного прогона пакета.

## 6. Единое решение о готовности

Сделать серверный результат проверки готовности с перечнем причин, пригодный для UI и повторно используемый при переключении. Не хранить независимо редактируемый флаг IsReady. Различать как минимум: недостаточно данных, проверка не пройдена, отчёт устарел, готово к включению. У каждой причины — стабильный код и понятное сообщение.

Политика первого этапа должна быть явной и версионированной, со следующими начальными настройками:

- минимум 1 различное контрольное имя и 1 оцениваемая контрольная единица;
- 0 регрессий на контроле;
- минимум 1 исправленная контрольная единица;
- число неправильных значений и число конфликтов на контроле не увеличиваются;
- нет конфликтующей разметки и ошибок исполнения;
- проходят прежние проверки пакета и учебных оснований.

Это минимальная защита пилота, не доказательство промышленной точности. Минимальные размеры выборки и требуемое число исправлений оформить проверяемыми настройками без ослабления по запросу клиента; фиксировать эффективную политику в отчёте. Изменение политики делает старый допуск устаревшим. Пороговые настройки не брать из случайных чисел в UI.

Версия без измеримого улучшения не получает обычный допуск. При этом сохранить существующее явное отключение активной версии до baseline: оно остаётся отдельным действием с причиной и expected sequence, не маскируется под успешный выпуск. Возврат к прежней версии требует новой актуальной оценки этой версии; автоматического отката не добавлять.

## 7. Актуальность и защита переключения

Перед включением под общим порядком блокировок и в свежей транзакции проверить:

- права и активность пользователя, область и принадлежность отчёта;
- выбранную версию, текущую активную конфигурацию и sequence;
- актуальность baseline-зависимостей и схемы характеристик;
- совпадение текущего допустимого состава контрольной выборки и её разметки со снимком;
- отсутствие отзыва/исключения/потери источников, актуальность evidence черновиков;
- применённую политику допуска и все существующие проверки активации.

Добавление подходящего подтверждения, изменение baseline, отзыв или исключение источника, изменение пакета либо переключение области после оценки должны обнаруживаться до записи нового Switch. Не доверять присланным клиентом метрикам, хешам, ready-флагам или reasons.

Проверить все конкурирующие пути записи. Gate этапа 4 уже защищает исключение, подтверждение, обучение и переключение, но сам по себе не защищает существующие изменения словаря, профилей, схем и отзыв подтверждения. Для зависимостей новой оценки обеспечить согласованный gate/ревизии/транзакционную защиту и документировать порядок. Проверка хеша перед транзакцией с последующим незащищённым переключением недостаточна. Не брать gate повторно из вложенного вызова.

Отчёт не связывать долгой транзакцией с пользовательским подтверждением. Устаревший допуск возвращает HTTP 409 с причиной и предложением создать новую оценку. Два конкурентных включения с одним expected sequence не создают два успешных переключения. Существующие активные знания при неудаче не меняются.

Закрыть обход через старый endpoint включения: для новой активации нужны новые данные сравнительной оценки независимо от клиента. Старые отчёты остаются читаемыми с отметкой «Исторический формат: требуется новая оценка для включения». Применённые ранее переключения и текущая работа старых версий сохраняются.

## 8. API и интерфейс

Расширить существующий путь работы с версией и отчётом. Один сценарий: выбрать версию → создать сравнительный отчёт → посмотреть исправления/регрессии/блокирующие причины → явно включить.

В интерфейсе показывать текущую версию, кандидата, область, размер и состав контроля, отдельные показатели пакета, результат учебной проверки, актуальность отчёта и причину недоступности включения. Длинные списки различий — с серверной пагинацией. После успешного переключения обновлять состояние и историю без перезагрузки страницы; ошибка не должна показывать успешное включение.

В отчёте нужны переходы к доступному происхождению примеров. После удаления импорта сохранённый отчёт доступен своему автору при текущих разрешениях, но включение с отсутствующим пакетом запрещено прежними проверками. Не предоставлять чужую разметку по знанию ReportId, ExampleId или FeedbackId.

Новые API ограничить активной учётной записью и DictionariesManage плюс существующими правилами владельца объектов. Проверять create/read/replay/readiness/switch на сервере. Предусмотреть лимиты размера снимка, количества выбранных единиц и времени вычисления. При превышении лимита вернуть явную ошибку, не обрезать выборку и не выпускать частичный успешный отчёт. Сохранить действующий лимит пакета 2000 строк; лимит контрольной выборки задокументировать отдельно.

## 9. Проверяемые сценарии

1. Текущая и предлагаемая конфигурации используют один baseline и те же общие правила распознавания, что импорт/preview; версия-кандидат не становится активной при оценке.
2. Один снимок при повторе даёт одинаковые результаты и знаменатели; изменения живых словаря/профилей не меняют старый отчёт. Неподдерживаемый формат не пересчитывается молча другим исполнителем.
3. Дубли не увеличивают знаменатель; конфликт разметки блокирует готовность. Пересечение имён по всем видам evidence не попадает в контроль. Нулевой контроль блокирует включение.
4. Правильные/неправильные/пропуски/конфликты и исправления/регрессии проверены на небольших известных наборах. Неразмеченные характеристики не искажают точность.
5. Улучшение без регрессий допускает выпуск при остальных выполненных условиях; регрессия, увеличение неправильных значений/конфликтов, отсутствие улучшения или недостаточный контроль блокируют прямой API-вызов.
6. После оценки изменение baseline, схемы, пакета, состава подтверждений, отзыв/исключение или смена активной версии делает отчёт непригодным для включения, не переписывая его историю.
7. Конкурентные включение/исключение, включение/отзыв, включение/изменение baseline и два включения дают согласованный результат. Ошибка проверки не оставляет частичного Switch.
8. Старый endpoint и отчёт старого формата не обходят новую проверку. Уже активная версия продолжает работать; явное отключение до baseline сохраняется.
9. После успешного включения новый запуск импорта и preview показывает новую версию и ожидаемый результат. Запуск, уже зафиксировавший контекст, сохраняет свой контекст.
10. Чужой, заблокированный пользователь и пользователь без права не получают отчёт/разметку и не могут включать версию. Cleanup сохраняет просмотр исторического снимка, но не даёт обойти условия новой активации.

Использовать изолированную PostgreSQL со штатными миграциями. Проверить реальный API для защиты включения, целевые backend-тесты, сборки API/frontend, TypeScript/ESLint. По возможности пройти браузерный сценарий. Явно перечислить незапущенные проверки. Рабочую базу и пользовательский dump не использовать.

## 10. Границы сдачи

Не объединять таблицы ради их количества, не заменять типизированные черновики универсальным JSON, не создавать полный экран управления всем жизненным циклом, автоматическое переобучение, автоматический выпуск, внешнюю ML-платформу или отдельную систему уведомлений. Не вводить обучение на контрольной выборке внутри оценки.

Результат: рабочие изменения и миграции, единый проверяемый путь оценки/включения, фактические результаты тестов, описание снимка и политики допуска, защита от гонок, совместимость старых отчётов и порядок развёртывания. Обновить архитектурную карту и создать `docs/architecture/learning-evaluation-release-implementation.md`. Отдельно назвать оставшуюся границу: словарные предложения имеют собственный управляемый выпуск; полная независимая внешняя оценка качества и упорядочение сроков хранения — последующие задачи.
