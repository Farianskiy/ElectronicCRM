# Сравнительная оценка и выпуск правил

Реализация этапа 5, 23.09.2026. Расширены существующие RuleSetReport, ActivationValidator и RuleSetSwitcher. Отдельной истории выпусков, очереди или механизма активных версий не добавлено.

## Пользовательский путь

На странице импорта пользователь выбирает подготовленную версию, запускает «Сравнить версии и проверить импорт», просматривает контроль, изменения по строкам, учебную проверку и операционный отчёт пакета. Включение остаётся отдельным подтверждённым действием с причиной и expected sequence. Новый запуск импорта и preview используют включённую версию через общий effective recognizer. Уже созданный контекст запуска сохраняет закреплённую версию.

Сохранённый отчёт можно открыть по его номеру в разделе распознавания, включая случаи удаления исходного импорта. Воспроизведение явно обозначено как историческое и не является разрешением включить версию. Новый выпуск требует доступного пакета и актуального отчёта.

## Контроль и учебные основания

Контроль строится только из собственных активных подтверждений области с доступным, не исключённым Feedback. Единица — нормализованное имя и характеристика. Повторные одинаковые значения не увеличивают знаменатель. Противоречивые значения блокируют допуск.

Все имена из evidence кандидата или текущей версии исключаются из контроля целиком, по всем характеристикам. Проверяются literal, integer и multi-integer evidence, включая checked. Эти имена показываются отдельно как учебная диагностика. Скрытые чужие подтверждения не выводятся в отчёте.

Добавлено минимальное поле `TrainingExample.IsEvaluationOnly` и обратимое действие назначения примера для контроля правил в существующей панели. Оно необходимо потому, что прежний TrainingCheck сверяет полный состав учебной выборки: без разделения новые контрольные имена одновременно меняли бы основания уже подготовленного черновика. Назначать контроль следует до подготовки версии. Изменение назначения существующего учебного основания требует новой подготовки/проверки; старые evidence не переписываются.

Контрольные примеры исключены из генерации/сохранения черновиков трёх видов и экспорта подтверждённых учебных примеров. Само назначение не исключает Feedback из отдельного фонового обучения словаря. Поэтому группа называется «Контроль без пересечения с основаниями правил», а не полностью независимая выборка. Историческое происхождение baseline может быть неизвестно. Для глобального запрета обучения сохраняется отдельное исключение источника.

## Снимок и повтор

В существующем отчёте добавлен nullable JSONB `evaluation_json`. Старый операционный `snapshot_json` сохранён. Формат сравнения — `1`, исполнитель — `effective-comparison-v1`. Снимок содержит область, текущую и предлагаемую исполняемые версии, sequence, применимые термины словаря, профили с конфигурацией, определения и схему характеристик, разметку с ExampleId/FeedbackId, имена пересечений, политику, обе стороны результатов, метрики и учебную проверку. Автор и время хранятся в самом отчёте.

Создание выполняется в RepeatableRead и не удерживает mutation gate на время вычисления. Отчёт может устареть сразу после создания; перед включением проводится новая проверка. SHA-256 вычисляется по каноническому JSON: свойства сортируются, числа нормализуются, коллекции формируются в определённом порядке. Вложенные конфигурации профилей также канонизируются.

Обе стороны используют один `CatalogEffectiveRecognitionService`: baseline + текущая версия и тот же baseline + кандидат вместо текущей версии. Для них создаются отдельные заполненные `CatalogRecognitionRunContext`. Повтор использует только сохранённые данные распознавания; живые чтения нужны для проверки доступа и загрузки самого отчёта. Позднее исключённые источники допустимы только в историческом повторе. Неизвестный формат/исполнитель возвращает явную ошибку.

## Допуск

Настройки `RecognitionEvaluation` проверяются при запуске:

| Параметр | По умолчанию |
| --- | --- |
| MinimumControlNames | 1 |
| MinimumControlUnits | 1 |
| MinimumImprovements | 1 |
| MaxExamples | 2000 |
| TimeoutSeconds | 60 |

Минимумы должны быть положительными и не превышать MaxExamples; MaxExamples ограничен 2000, время — 120 секундами. Политика `release-policy-v1` запрещает любую регрессию и увеличение числа неправильных значений или конфликтов. Конфликт разметки запрещает выпуск. Прежние проверки пакета и учебных оснований остаются обязательными.

Метрики: правильно, неправильно, пропуск, конфликт — с общим явным знаменателем; исправления и регрессии; разрез характеристик; отдельная учебная диагностика. При нулевом знаменателе доля отсутствует. Состояния: Ready, Failed, InsufficientData, Stale; исторический повтор — Historical. Это минимальный допуск пилота, а не доказательство промышленной точности.

Лимиты: пакет — 2000 строк; входных подтверждений до дедупликации — MaxExamples; применимых терминов — 10000; определений/профилей — 1000; исходных различных evidence-имён — 20000; JSON сравнения — 8 миллионов байт UTF-8. При превышении возвращается ошибка без сохранения частичного отчёта. Создание и повтор ограничены временем. Выдача различий — по 25 строк на серверной странице.

## Актуальность, права и конкуренция

Новая активация через прежний endpoint обязательно проходит сравнительную проверку. Старые отчёты остаются читаемыми, но не позволяют включить версию. Существующие активные версии продолжают работать; явное отключение до baseline с причиной и expected sequence сохранено. Возврат к старой версии требует новой оценки.

Проверяются активность пользователя, DictionariesManage и авторство отчёта; создание дополнительно проверяет принадлежность пакета. Изменения baseline, схемы, собственной допустимой разметки, назначения примеров, политики или текущей версии меняют отпечаток. Пакет и учебные основания дополнительно проверяются прежним валидатором. Устаревший отчёт не создаёт Switch.

Порядок включения: общий session advisory gate `72639482022` → новая Serializable-транзакция → свежие чтения/проверки → запись Switch → commit → освобождение gate. Gate теперь использует то же соединение DbContext: это позволяет безопасно совместить его с транзакционными блокировками SQL-триггеров.

Миграция добавляет BEFORE STATEMENT триггеры на запись словаря, профилей, определений/схемы, производителей/типов, примеров/feedback, пакетов/строк и switches. Триггер берёт тот же `pg_advisory_xact_lock` до блокировок строк; это покрывает и ExecuteUpdate/Delete старых путей. Поэтому изменения зависимостей не могут вклиниться между проверкой и записью Switch. Цена решения — общая сериализация записей перечисленных таблиц между областями. Длительную пользовательскую паузу внутри транзакции не держим. Другой gate фонового прохода сохранён.

## API

- Существующие создание отчёта и включение версии сохранены.
- `GET /api/catalog/recognition/training/rule-set-reports/{id}/evaluation?page=1` — сохранённый результат и актуальная готовность.
- `POST /api/catalog/recognition/training/rule-set-reports/{id}/evaluation/replay?page=1` — исторический повтор без изменения отчёта.
- `POST /api/catalog/recognition/training-examples/{id}/purpose` с `evaluationOnly` — назначение собственного активного примера.

## Развёртывание

Миграция `20260923070737_AddRecognitionComparativeEvaluation` добавляет два поля и триггеры. Предшествующие миграции жизненного цикла и исключения источника обязательны. Рабочая БД в ходе реализации не использовалась, миграция к ней не применялась.

Остановить API/воркеры старой версии, выполнить штатное резервное копирование и применить миграции установленным способом, затем запустить обновлённый API и frontend. Одновременная работа старого session gate на отдельном соединении и новых SQL-триггеров не поддерживается: переход требует согласованного обновления экземпляров. Проверить готовность API, просмотр старого отчёта, новую оценку и явное включение на согласованной пилотной области. Автоматического включения после миграции нет. При откате к прежнему приложению сначала требуется согласованный откат этой миграции при остановленных процессах; это удаляет новые снимки и назначения контроля.
