# Этап 3. Управление подтверждёнными примерами и явные источники обучения

Дата: 2026-09-22. Выполнить реализацию непосредственно в проекте. Сохранить предыдущие изменения фонового обучения и общего распознавания, а также чужие незакоммиченные изменения. Не ограничиваться планом, тестами или кодом для ручной вставки.

## Результат для пользователя

Пользователь видит подтверждённые обучающие примеры в отдельном разделе, может отозвать своё подтверждение даже после удаления исходного импорта и выгрузить именно действующие подтверждённые примеры. Система явно различает подтверждение примера и обратную связь после проверки импорта. У каждого источника понятны назначение и последствия отзыва.

## Зафиксированное поведение

Сохранить два уровня достоверности, не склеивать их в один статус:

| Данные | Как появляются | Кто использует | Последствие отзыва подтверждения |
|---|---|---|---|
| Проверенная обратная связь (feedback) | Существующая финализация при применении импорта | Фоновое накопление кандидатов; существующий экспорт feedback | Не изменяется: проверка импорта и подтверждение фрагмента — разные решения |
| Подтверждённый пример (TrainingExample) | Явное подтверждение имени, области, значения и фрагмента | Генерация/проверка черновиков; новый экспорт подтверждённых примеров | Отозванная запись исключается из новых выборок этих потребителей |

Название действия в интерфейсе: «Отозвать подтверждение примера». Оно не обещает забыть все сведения о товаре, отозвать feedback или отключить уже действующие правила. Это пояснение должно быть видно рядом с действием и в выборе экспорта.

Не переводить всё обучение на обязательное ручное подтверждение. Не менять существующую политику финализации feedback. Глобальный запрет использования ошибочного наблюдения с пересчётом накопленных кандидатов — другой механизм; не маскировать его отзывом TrainingExample.

## 1. Общие правила выбора данных

Выделить именованные политики/запросы для ReviewedFeedback и ConfirmedExamples. Не создавать универсальный workflow или сущность с десятками состояний.

- ReviewedFeedback сохраняет нынешние условия Finalized, IsTrainingEligible, cutoff и дополнительные требования конкретного потребителя. Например, агрегатор по-прежнему использует свои типы feedback и область производителя.
- ConfirmedExamples выбирает активные TrainingExamples по области. Источник истины — сохранённый снимок примера, включая подтверждённый span. Значения не восстанавливаются из изменяемой строки импорта.
- TrainingSampleReader, новый экспорт и список примеров используют согласованные критерии активности и области. Пагинация выполняется в БД; не загружать всю таблицу для фильтрации.
- Отозванный пример остаётся в истории. Повторное подтверждение создаёт новую запись по существующим правилам, не стирает отзыв старой. Сохранить уникальность активного примера по SourceFeedbackId.
- Не добавлять требование Finalized для TrainingExample, если его не было: существующее явное подтверждение может предшествовать применению импорта.

## 2. Отвязать управление от срока жизни импорта

Добавить API списка/просмотра подтверждённых примеров и отзыва по ExampleId без обязательных BatchId/RowId. На существующей странице распознавания добавить раздел «Обучающие примеры» с серверной пагинацией и фильтрами по производителю, типу, характеристике и состоянию активен/отозван.

Показывать имя товара, подтверждённый фрагмент, значение, область, дату подтверждения и состояние; дату отзыва — если есть. Ссылка на исходный импорт необязательна. После его удаления писать «Исходный импорт удалён», не скрывать сам пример и не возвращать ошибку на карточку.

Существующий путь отзыва из импорта сохранить как совместимый адаптер. Он проверяет принадлежность примера переданным пакету/строке, затем использует общую операцию. Новый путь не зависит от наличия пакета, строки и их ссылок в feedback.

Авторизация: активная учётная запись, существующее право DictionariesManage, управление своими подтверждениями по ConfirmedByUserId. Не расширять доступ всем владельцам DictionariesManage к чужим примерам. Если в проекте уже есть явно определённое административное полномочие управления чужими примерами, использовать его последовательно; не выводить такое полномочие из одного названия роли. Проверки должны выполняться на сервере, включая list/get/revoke. Области обучения остаются общими для существующих внутренних потребителей; ограничение управления своими примерами не должно незаметно фильтровать генератор по текущему пользователю.

Отзыв повторяемый: второй запрос успешен и не меняет первоначального автора/время отзыва. Обновление атомарное; конкурентные запросы не создают двойного события и не возвращают пример в активное состояние.

Причину отзыва сделать обязательной для новых действий и сохранить рядом с существующими полями отзыва. Старым отозванным записям не выдумывать причины. Допускается одна аддитивная миграция существующей таблицы; новую таблицу жизненного цикла не создавать. Обновить старую кнопку/контракт отзыва совместимо: для старого клиента без причины использовать явно обозначенную техническую отметку старого API, а не выдавать её за введённый пользователем текст.

## 3. Сделать источник экспорта явным

В существующей панели экспорта разделить:

- «Проверенная обратная связь» — текущий экспорт с прежней семантикой и форматом. Подписать, что он может содержать записи без явного подтверждения обучающего фрагмента и не меняется от отзыва TrainingExample.
- «Подтверждённые примеры» — новый версионированный JSONL-экспорт действующей явной разметки. Его выборка согласована с ConfirmedExamples и существующими правами экспорта; не выдавать новый доступ к чужим данным через новый endpoint.

Для нового формата включить ExampleId, SourceFeedbackId, ManufacturerId, ProductTypeId, CharacteristicDefinitionId, имя, raw value, normalized value, подтверждённые SpanStart/SpanLength, ConfirmedAtUtc и версию формата. Отдельно указать SelectionAsOfUtc и выбранную область в метаданных ответа/экспорта. Явно описать единицы span: используемые .NET UTF-16 позиции. Не записывать подтверждённый span в поля SuggestedSpan и не объявлять пример автоматически AcceptedSpan, если это исправленная разметка.

Экспорт берёт согласованную выборку на начало чтения через подходящую транзакцию/снимок. Отзыв, завершённый до начала нового экспорта, исключает запись. Отзыв во время уже начатого экспорта не обязан переписывать его снимок. Исторический cutoff не обещает восстановить состояние на любую прошлую дату: помечать новую выгрузку как снимок действующей разметки на момент формирования.

Существующие bundle-экспорт, split-алгоритм и валидатор старого формата сохранить. Новый формат не передавать старому валидатору как совместимый. Bundle и train/test split для нового источника на этом этапе не добавлять: это следующий этап оценки качества. Уже скачанные выгрузки не изменяются при отзыве — сообщить это в интерфейсе.

## 4. Последствия для правил

Проверить существующие recheck и activation validator для literal/integer/multi-integer. Новые генерации не используют отозванный ExampleId. Черновик, основанный на нём, не должен проходить проверку неизменности оснований; версия с такими основаниями не должна заново активироваться через обход проверок.

Исторические evidence, версии и отчёты не удалять. Уже активную версию не отключать автоматически при отзыве. В результате операции и интерфейсе явно сообщить, что действующие правила остаются активными и для их изменения требуется отдельная проверка/переключение. Не заявлять, что конкретная версия затронута, без проверки связи по evidence.

Не пересчитывать задним числом статистику кандидатов из feedback в этой задаче: отзыв конкретного подтверждения не отзывает отдельное решение о проверке импорта.

## Приёмка в составе реализации

1. Подтверждённый пример виден в списке и новом экспорте; генератор читает ту же активную запись.
2. После отзыва он виден в истории, отсутствует в новом экспорте и текущей учебной выборке; причина, автор и время сохранены.
3. ReviewedFeedback и его старый экспорт сохраняют прежнее поведение; интерфейс явно объясняет различие.
4. Удаление просроченного исходного импорта реальным cleanup не лишает владельца просмотра и отзыва примера. Проверить на изолированной PostgreSQL со штатной схемой.
5. Чужой пользователь не получает просмотр/отзыв через подмену ExampleId; неактивный пользователь и пользователь без права получают отказ.
6. Повторный и конкурентный отзыв сохраняет первую запись отзыва; повторное подтверждение не стирает историю.
7. Все виды черновиков корректно реагируют на отзыв основания; действующая версия не выключается молча.
8. Новый экспорт корректно передаёт исправленный span и Unicode; старый экспорт и его bundle остаются совместимыми.
9. Предыдущие гарантии импорта, общего распознавания и фонового обучения сохранены.

Проверки писать вместе с изменением; не делать отдельный предварительный этап тестов. Выполнить целевые backend-проверки и frontend typecheck/build; по возможности проверить браузерный сценарий подтверждение → список → экспорт → отзыв → повторный экспорт. Указать, если браузерная проверка не выполнялась. Не использовать рабочую БД или пользовательский dump.

## Что вернуть

Внесённые изменения, миграцию при необходимости, обновлённую архитектурную карту и фактические результаты проверок. Коротко описать, где теперь найти примеры, что означает отзыв и какой экспорт выбирать. Не возвращать код для ручной вставки. Следующие этапы автоматически не выполнять.
