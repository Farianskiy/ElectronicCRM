# Задание 01: зафиксировать поведение импорта и обучения

> ОТМЕНЕНО как обязательный первый этап 2026-09-21. Не выполнять отдельный проект тестирования. Актуальное задание на реализацию: `docs/architecture/implementer-task-import-learning.md`. Проверки выполнять в составе реального изменения.

## Цель

Подготовить проверяемую основу для разделения импорта, распознавания и обучения. Прочитать `docs/architecture/import-learning-audit.md`. Выполнить только этот этап; архитектурный рефакторинг будет отдельным заданием.

## Границы

Разрешены тесты, тестовые данные и документация результатов. Производственный код, API и миграции на этом этапе не менять. Не обращаться к рабочей БД и не использовать пользовательский dump; тесты сохранения выполнять на изолированной тестовой БД по существующим правилам проекта. Не делать новую универсальную тестовую платформу.

## Работа

1. Проверить инструкции репозитория и текущее состояние. Запустить существующие тесты импорта и распознавания, записать исходные сбои отдельно. Не объявлять их результатом нового изменения.
2. Проследить и проверить F1: одинаковое имя, производитель и тип, baseline не даёт значения, активный набор даёт. Сравнить кандидатов/конфликты обычного preview и import enrichment. Зафиксировать текущую разницу и обозначить тест как описание существующего поведения, которое изменится на этапе 02.
3. Проверить F2: применение импорта фиксирует товары и feedback, затем вызывает общую обработку кандидатов. Проверить, что ошибка этой обработки из предусмотренной ветки обработки ошибок не отменяет товары. Указать фактический способ продолжить обработку без нового импорта либо его отсутствие. Не выдавать вызов агрегатора вручную из теста за существующую функцию продукта.
4. Проверить F3 на настоящем запросе PostgreSQL: более 500 Accepted feedback; первые 500 не имеют подходящего кандидата, за ними есть запись с существующим кандидатом. Повторить агрегацию и проверить, достигается ли последняя запись. Если тест подтверждает голодание очереди, записать ожидаемое исправление для этапа 03. Проверка на поддельном репозитории не заменяет проверку сортировки и Take.
5. Проверить F4: один finalized, training-eligible feedback с подтверждённым примером; отозвать пример. Сравнить выдачу TrainingSampleReader и DatasetReader. Зафиксировать, что именно отзывается сейчас; не менять политику автоматически.
6. Если F1–F4 закрыты и среда позволяет, добавить проверку F8: cleanup удаляет просроченный редактируемый пакет с подтверждённым примером; проверить сохранность примера, связи feedback и доступность отзыва. Если сценарий блокируется ограничениями реальной схемы, записать это как результат вместо предполагаемого исхода.

## Критерии готовности

- Есть воспроизводимые тесты на существенное поведение, а не на количество вызовов внутренних методов.
- Результаты различают «подтверждено тестом», «опровергнуто», «не удалось проверить».
- Для каждого нового теста указано, защищает ли он обязательное поведение или временно описывает различие, которое предстоит исправить.
- Существующие проверки сохранения ручных исправлений, конфликтов Excel/распознавания и активных правил не ухудшены.
- В `docs/architecture/implementation-01-results.md` записаны сценарии, команды, результаты, ограничения среды и рекомендации к этапам 02–03.
- В итоговом сообщении перечислены изменённые файлы и фактические результаты запусков. Нет заявления о прохождении незапущенных тестов.

## Передача планировщику

Предоставить diff и отчёт. Следующий этап выбирается по подтверждённым результатам. Не объединять исправление очереди, изменения схемы знаний и унификацию распознавания в один большой рефакторинг.
