# Задание: безопасное определение характеристик по существующему каталогу

## 1. Цель этапа

После предыдущего этапа импорт умеет определять тип товара по похожим товарам существующего каталога. На контрольном смешанном файле все восемь строк получили правильный тип без колонок типа и характеристик.

Оставшаяся проблема: часть характеристик не извлекается из названия и остаётся с предупреждениями `characteristic.low_confidence` или `characteristic.required`. В проекте уже есть поиск аналогов, предложения характеристик, версии конфигурации, режимы `Off / Shadow / Suggest / AutoFill`, происхождение значений и защищённый выпуск конфигурации. Нельзя создавать ещё один параллельный механизм обучения.

Нужно довести существующий механизм аналогов до безопасного автоматического дополнения характеристик:

1. явно записанное в названии или Excel значение всегда главнее аналогов;
2. аналоги выбираются внутри правильного семейства товара, а не только по общим словам;
3. автоматически переносятся только устойчивые признаки семейства;
4. переменные параметры конкретной модели не угадываются;
5. каждое дополненное значение имеет объяснимое происхождение и не становится учебной истиной без подтверждения пользователя.

## 2. Что считается правильным результатом

Для названия вида `Авт. выкл. AV 10 1P 13A 10кА ...` система должна:

- определить тип по каталогу, если строгого термина недостаточно;
- извлечь `1P`, `13 A`, `10 кА` непосредственно из названия;
- не заменять эти значения данными похожего товара;
- найти товары того же производителя, типа и семейства `AV 10`;
- предложить или автоматически заполнить только одинаковые у достаточного числа членов семейства признаки, например серию, наличие теплового расцепителя или иной действительно постоянный атрибут;
- не переносить с аналога другой номинальный ток, число полюсов, диапазон тока, ток утечки или отключающую способность, если этих значений нет в исходном названии и они различаются внутри семейства;
- показать пользователю, какие товары послужили основанием и почему значение было заполнено либо заблокировано.

## 3. Границы задачи

Входит в этап:

- импорт и повторный анализ строк импорта;
- существующий поиск аналогов каталога;
- конфигурации аналогового распознавания для области `производитель + тип товара`;
- происхождение, подтверждение и отклонение предложений;
- экран строки импорта и рабочее пространство обучения;
- автоматические и ручные проверки на существующих типах: модульные автоматы, мотор-автоматы, дифференциальные автоматы и УЗО.

Не входит в этап:

- машинное обучение, embeddings или внешний ИИ;
- автоматическое создание новых типов и характеристик;
- автоматический выпуск правил или словаря без оценки и подтверждения;
- изменение цен, остатков и артикулов;
- копирование всех характеристик одного «самого близкого» товара;
- использование значений, полученных по аналогии, как подтверждённых учебных примеров.

## 4. Этап 1. Зафиксировать матрицу характеристик

### 4.1. Классы значений

Для каждой характеристики выбранного типа определить одну из политик:

- `ExplicitOnly` — только Excel, ручной ввод или строгое извлечение из названия;
- `Suggest` — аналогия может показать предложение, но не заполняет поле;
- `AutoFill` — аналогия может заполнить пустое поле после выполнения строгих порогов;
- `Off` — аналогия для этой характеристики не используется.

Использовать существующие режимы конфигурации как источник истины. Если необходимо различать `ExplicitOnly` и `Off`, не вводить второй несвязанный справочник: расширить одну существующую конфигурацию с обратной совместимостью.

### 4.2. Начальная безопасная политика

По умолчанию оставить `Suggest`. `AutoFill` разрешать только явно для конкретной характеристики в выпущенной конфигурации области.

Характеристики варианта модели должны остаться `ExplicitOnly` или `Suggest`, но не `AutoFill`. К ним относятся как минимум:

- номинальный ток;
- диапазон тока;
- количество полюсов;
- ток утечки;
- отключающая способность;
- иные размеры, исполнения и номиналы, способные различаться внутри одной серии.

Стабильные признаки семейства можно переводить в `AutoFill` только после оценки на контрольных товарах.

### 4.3. Диагностика

В рабочем пространстве показывать для каждой характеристики:

- действующий режим;
- текущие пороги;
- количество подходящих аналогов;
- победившее значение и альтернативы;
- причину, по которой автозаполнение разрешено или запрещено.

## 5. Этап 2. Усилить выбор семейства аналогов

Текущий фильтр `производитель + тип` недостаточен: общие слова вроде `автомат`, `выключатель`, `1P` не доказывают принадлежность к одной серии.

### 5.1. Семейный якорь

Добавить детерминированное выделение семейного якоря из названия и артикула. Якорем могут быть:

- обозначение серии: `AV 10`, `ПРК32`, `АВДТ32`, `АД12`, `ВД1-63`;
- устойчивый буквенно-цифровой токен артикула;
- подтверждённый словарный термин серии.

Не привязывать алгоритм только к перечисленным сериям. Они являются контрольными примерами, а не захардкоженным списком.

### 5.2. Правила допуска кандидата

Кандидат допускается в доказательства характеристик, если:

1. совпадают производитель и тип;
2. совпал семейный якорь либо есть достаточно сильная комбинация имени, артикула и уже известных характеристик;
3. нет конфликта по характеристике, объявленной идентификатором семейства;
4. кандидат не архивный и не является текущим товаром;
5. кандидат имеет известное происхождение значений, используемых как доказательство.

Различия по вариантным характеристикам не должны исключать кандидата из доказательств для других полей. Например, `13 A` и `16 A` могут быть товарами одной серии, но значение `16 A` нельзя переносить в строку `13 A`.

### 5.3. Объяснимость

В результат совпадения добавить:

- найденный семейный якорь;
- признаки, по которым кандидат включён;
- признаки, по которым кандидат исключён;
- уровень сходства;
- идентификатор снимка кандидатов.

Результат должен быть детерминированным при одинаковом снимке каталога.

## 6. Этап 3. Единый порядок заполнения строки

Закрепить один порядок приоритетов:

1. ручное значение пользователя;
2. корректное явное значение из Excel;
3. строго распознанное значение из названия;
4. ранее подтверждённое пользователем решение;
5. `AutoFill` из действующей конфигурации аналогов;
6. предложение с низкой уверенностью, которое не записывается в значение;
7. пустое значение с понятным предупреждением.

Нижестоящий источник никогда не заменяет вышестоящий. Повторный анализ обязан сохранять ручные значения и подтверждения.

Перед применением аналогии нормализовать значение тем же нормализатором, который используется для Excel и распознавания. Невалидное значение блокировать с диагностикой, а не сохранять как строку.

После дополнения повторно запускать штатную валидацию строки, чтобы исчезали только действительно устранённые `characteristic.required` и `characteristic.low_confidence`.

## 7. Этап 4. Происхождение и защита обучения

Для каждого значения из аналогов сохранять:

- источник `CatalogAnalogy`;
- идентификатор и номер активной конфигурации;
- хэш конфигурации;
- снимок кандидатов;
- идентификаторы поддерживающих товаров;
- число поддерживающих товаров и долю согласия;
- семейный якорь;
- дату расчёта.

Значение `CatalogAnalogy`:

- не создаёт подтверждённый учебный пример автоматически;
- не участвует как независимое основание следующего обучения, иначе появится самоподтверждающийся цикл;
- может стать учебным основанием только после явного подтверждения пользователем;
- при изменении или удалении поддерживающих товаров помечается устаревшим и пересчитывается при повторном анализе.

Если существующая модель происхождения уже хранит все необходимые данные, новую миграцию не создавать. Если данных не хватает, добавить одну миграцию и описать порядок её применения.

## 8. Этап 5. Интерфейс пользователя

### 8.1. Строка импорта

Для каждого поля показывать источник человеческим языком:

- `Из Excel`;
- `Распознано в названии`;
- `Подтверждено вручную`;
- `Заполнено по похожим товарам`;
- `Только предложение — требуется решение`.

Для аналогии добавить действие `Почему?`, раскрывающее семейство, поддержку, альтернативы и список товаров-оснований.

### 8.2. Массовая работа

На уровне пакета показать счётчики:

- заполнено строго;
- заполнено по аналогам;
- ожидает подтверждения;
- заблокировано конфликтом;
- осталось обязательных пустых значений.

Добавить фильтр строк по этим состояниям. Не заставлять пользователя открывать каждую строку, чтобы понять итог анализа.

### 8.3. Рабочее пространство обучения

На экране конфигурации области дать возможность последовательно:

1. увидеть статистику `Shadow`;
2. перевести характеристику в `Suggest`;
3. оценить черновик на контрольных товарах;
4. при отсутствии регрессий выпустить `AutoFill`;
5. вернуть предыдущую конфигурацию через новый черновик и новую оценку.

Не добавлять скрытую кнопку, мгновенно включающую `AutoFill` в обход существующего выпуска.

## 9. Этап 6. Автоматические проверки

### 9.1. Модульные тесты

Обязательные сценарии:

1. явное значение из Excel не заменяется аналогией;
2. строгое значение из названия не заменяется аналогией;
3. ручное значение сохраняется при повторном анализе;
4. одна серия с разными токами даёт предложение стабильной характеристики, но не копирует ток;
5. совпадение только по общему слову не считается семейством;
6. товары другого производителя или типа не участвуют;
7. конфликт значений или равенство лидеров блокирует заполнение;
8. недостаток товаров блокирует заполнение;
9. `Shadow` считает результат, но не показывает и не заполняет;
10. `Suggest` показывает, но не заполняет;
11. `AutoFill` заполняет только пустое разрешённое поле;
12. невалидное нормализованное значение отклоняется;
13. значение из аналогии не становится учебным примером без подтверждения;
14. отзыв подтверждения создаёт допустимое учебное основание;
15. изменение конфигурации или снимка помечает старое основание устаревшим;
16. одинаковый снимок даёт одинаковый результат и порядок кандидатов.

### 9.2. Интеграционные тесты

Проверить полный цикл:

`каталог → импорт без типа и характеристик → определение типа → строгое распознавание → аналоговые предложения → подтверждение/отклонение → повторный анализ → применение пакета`.

Отдельно проверить конкуренцию повторного анализа, изменения конфигурации и сохранения строки.

### 9.3. Производительность

Кандидаты каталога и активная конфигурация должны загружаться снимком и переиспользоваться на пакет. Не допускать отдельного полного запроса каталога для каждой строки. Зафиксировать верхнюю границу размера пула и количество запросов интеграционным тестом.

## 10. Этап 7. Ручной приёмочный сценарий

Использовать файлы из:

`F:\Projects\ElectronicCRM\outputs\real-catalog-learning-test`

Проверить:

1. файлы 01 и 02 без колонок характеристик;
2. первичную базу 03 и 04;
3. смешанный файл 05 без типа и характеристик;
4. новый файл 06 с неизвестными номиналами внутри уже известных серий;
5. новый файл 07 с похожими общими словами, но другой серией, чтобы убедиться в отсутствии ложного переноса.

Для файла 05 сохранить текущий обязательный результат: `8 корректных / 0 ошибок`, правильные четыре типа. Дополнительно проверить источники каждой характеристики и отсутствие переноса вариантных значений.

Файл 06 должен показать, что система обобщает знания семейства на новую модель, но сохраняет её собственные номиналы из названия.

Файл 07 не должен получить автоматические характеристики при недостаточном семейном основании.

## 11. Порядок реализации

Работу выполнять небольшими проверяемыми частями:

1. тестами зафиксировать текущий результат и матрицу безопасных характеристик;
2. реализовать семейный якорь и диагностику отбора кандидатов;
3. усилить оценку предложений без изменения режима действующей конфигурации;
4. подключить единый порядок источников при импорте и повторном анализе;
5. дополнить происхождение и защитить учебный цикл от самоподтверждения;
6. обновить интерфейс строки и пакетные счётчики;
7. выпустить тестовую конфигурацию сначала в `Shadow`, затем в `Suggest`;
8. оценить конфигурацию на контрольных товарах;
9. включить `AutoFill` только для доказанно стабильных характеристик;
10. пройти файлы 01–07 вручную и зафиксировать результат.

После каждого пункта проект должен собираться, а существующие тесты оставаться зелёными.

## 12. Критерии готовности

Этап завершён, если одновременно выполнено следующее:

- тип товара по-прежнему определяется без ручного выбора на смешанном файле;
- явные значения из Excel, названия и ручного ввода никогда не заменяются аналогами;
- стабильные отсутствующие характеристики могут быть дополнены по выпущенной конфигурации;
- вариантные параметры не переносятся между моделями;
- общее слово без семейного основания не приводит к автозаполнению;
- пользователь видит источник и основания каждого значения;
- аналоговое значение не обучает систему само на себе;
- отзыв или изменение основания корректно инвалидирует результат;
- повторный анализ детерминирован и не создаёт дубликаты обратной связи;
- все unit, integration, API build, frontend build, TypeScript и ESLint проходят;
- ручные файлы 01–07 пройдены, а результаты записаны в отдельный отчёт реализации;
- миграции, если они понадобились, добавлены, но не применяются к рабочей БД без отдельного решения пользователя.

## 13. Ожидаемый итог этапа

После этого импорт будет использовать три независимых уровня знания в одном управляемом цикле:

1. строгие факты из Excel и названия;
2. безопасные выводы по существующим товарам той же семьи;
3. подтверждения пользователя, которые уже могут участвовать в обучении и выпуске правил.

Система не будет требовать строгого фрагмента названия для каждого свойства, но и не станет угадывать характеристики одного товара по случайно похожему другому товару.
