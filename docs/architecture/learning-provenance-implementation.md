# Этап 4: происхождение знаний и исключение наблюдений

Реализация добавляет просмотр сохранённых зависимостей и необратимое через API исключение конкретного Feedback. Новые таблицы и фоновые очереди не вводятся.

## Поведение

- Отзыв TrainingExample остаётся отдельной операцией над собственным подтверждением. Он не исключает Feedback.
- Исключение Feedback сохраняет время, пользователя и причину в `ExcludedAtUtc`, `ExcludedByUserId`, `ExclusionReason`. Повторный запрос возвращает первоначальное решение. Status, LabelQuality, IsTrainingEligible и исторические evidence сохраняются.
- `ReviewedFeedback` и `ConfirmedExamples` запрещают новые учебные выборки из исключённого источника. Отсутствующий источник также запрещает использование подтверждения. Применяется к агрегации, feedback JSONL/bundle, confirmed-examples-v1, генерации, сохранению и перепроверке трёх видов черновиков. Подтверждение нового примера проверяет источник под общей блокировкой.
- Текущие счётчики кандидата пересчитываются по оставшимся допустимым evidence. DistinctProductCount считает разные NormalizedProductName; допускается ноль. Evidence, SuggestionId, решения и исторический диапазон FirstSeen/LastSeen не удаляются.
- Основания pending suggestion проверяются независимо от статуса кандидата. Одобрение требует актуального EvidenceRevision и достаточных оснований; устаревший/отсутствующий revision или недостаточные основания возвращают HTTP 409. Содержание предложения не переписывается.
- Уже выпущенные термины и активные версии продолжают работать. Просмотр зависимостей показывает необходимость пересмотра. Активность версии определяется последним переключением области, а не наличием версии. Ручное исправление словаря и проверка/переключение правил остаются существующими отдельными действиями.

## API и интерфейс

Базовый путь `/api/catalog/recognition/learning-provenance`:

- `GET examples/{id}?page=1` — происхождение по примеру.
- `GET feedback/{id}?page=1` и `GET feedback/{id}/preview-impact?page=1` — происхождение и предварительное влияние.
- `POST feedback/{id}/exclude`, тело `{ "reason": "..." }` — исключение и фактические зависимости в той же транзакции.
- `GET suggestions/{id}` — актуальные показатели, достаточность и revision для одобрения.

Списки примеров, кандидатов, связей с черновиками, версиями и переключениями ограничены 25 записями на страницу каждый; ответ содержит полные счётчики списков. Связи строятся только по сохранённым идентификаторам. Проверочное evidence отделено от поддерживающего. Совпадения текста не восстанавливают историю.

На странице распознавания у примера есть «Использование в обучении», отдельная форма исключения с причиной и предварительным влиянием. Результат остаётся видимым после обновления списка активных примеров. Есть фильтр «Источник исключён», отдельные поля отзыва и исключения, состояние недоступного источника. На странице предложений словаря показаны текущие основания и действие их обновления.

Для каждой операции нужны активная учётная запись и DictionariesManage. Исключение finalized feedback разрешено его ReviewedByUserId; pending — владельцу существующего пакета. Собственное подтверждение даёт просмотр зависимостей, но не право исключать чужое наблюдение. Чужие подтверждения возвращаются только как ID и состояние. Права существующих экранов и действий не расширяются. После cleanup finalized feedback остаётся управляемым по сохранённому автору решения.

## Конкуренция и транзакции

`RecognitionMutationGate` использует общий PostgreSQL session advisory lock `72639482022` на отдельном непулируемом соединении в исходной реализации этапа 4. В этапе 5 он переведён на соединение DbContext для совместимости с транзакционными SQL-триггерами; актуальный порядок развёртывания описан в [learning-evaluation-release-implementation.md](learning-evaluation-release-implementation.md). Порядок: получить gate → сбросить только неизменённые tracked-сущности → начать транзакцию (если нужна) → прочитать актуальное состояние → сохранить/commit → освободить gate. Вход с незавершёнными изменениями или уже открытой транзакцией запрещён.

Gate используется исключением, страницей агрегации, promotion, одобрением, подтверждением примера, сохранением черновиков и активацией версии. Он отличен от lock всего фонового прохода; фон держит свой lock и затем берёт gate на отдельную страницу. Другие команды не берут lock фонового прохода. При активации gate берётся до Serializable-транзакции нового контекста.

Исключение и пересчёт кандидатов выполняются одной транзакцией. Ошибка пересчёта откатывает уже записанное исключение. Ответ строится по фактическим зависимостям и отдаётся только после commit; ожидания между открытием формы и её подтверждением нет. Одобрение использует единый SaveChanges для термина, предложения и кандидата, удерживая gate до завершения записи.

Экспорты не держат mutation gate. Уже начавшая SQL-снимок выгрузка может закончить старый набор; новая после commit отфильтрует источник независимо от cutoff. Скачанные файлы, evidence и старые отчёты не переписываются. Повторный анализ импорта сохраняет исключённые наблюдения вместо удаления pending feedback.

## Миграция и эксплуатация

`AddLearningSourceExclusion` добавляет три поля исключения, согласованность решения, EvidenceRevision и разрешает нулевые счётчики кандидатов. Рабочая база и пользовательский dump не использовались; миграция применялась только fixture к временной PostgreSQL 18 в Docker. При развёртывании остановить старые экземпляры API/worker, применить миграцию и запустить обновлённые экземпляры вместе: старые бинарные файлы не соблюдают новый запрет и общий gate. Откат старых ограничений требует отдельно обработать существующих кандидатов с нулевым вкладом; Down не удаляет их автоматически.

## Проверки

- Проверены реальные SQL-запросы происхождения, обе цепочки, пагинация, права автора примера/решения, запрет для заблокированной учётной записи, права pending-источника до и после cleanup, доступ после удаления импорта, сохранение исходного решения при повторе.
- Проверены пересчёт Accepted/Corrected/Rejected и одинаковых имён до нуля, сохранение evidence, исключение из dataset reader и confirmed export, запрет нового подтверждения, recheck и сохранения трёх видов черновиков после изменения источника.
- Проверены сохранение активности версии, определение активности по последнему переключению, сохранение выпущенного словарного термина, недостаточные основания и устаревший revision.
- Проверены конкурентные exclusion/learning (aggregation/promotion), exclusion/approval и повторное исключение; искусственная ошибка пересчёта откатывает транзакцию.
- Целевые проверки: 32 unit и 22 интеграционных сценариев. API собирается в отдельной конфигурации Provenance, поскольку Debug-файлы заняты запущенным приложением. Рабочий процесс не останавливался.
- Frontend: production build, TypeScript, ESLint. Браузерный E2E и отдельный HTTP E2E не запускались; интеграционные проверки вызывают реальные обработчики и PostgreSQL-репозитории.
- Restore интеграционных тестов выполнялся с временным `NuGetAudit=false` из-за существующего advisory SSH.NET; постоянные настройки не менялись.

Следующий этап единой оценки и выпуска не выполнялся.
