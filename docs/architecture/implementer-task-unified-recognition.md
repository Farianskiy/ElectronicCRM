# Следующее изменение: единое распознавание для импорта и диагностики

Внести реализацию непосредственно в проект. Предыдущая работа по фоновой обработке знаний уже внесена; сохранить её и имеющиеся незакоммиченные изменения. Это отдельный законченный этап, не повторный аудит и не отдельный проект тестирования.

## Проблема и результат

Сейчас CatalogImportRecognitionEnrichmentService объединяет базовое распознавание с активными наборами правил. PreviewCatalogProductNameRecognitionQueryHandler вызывает только базовый сервис; его запрос даже не содержит ManufacturerId. Поэтому результат, выученный и включённый для импорта, может отсутствовать на странице диагностики.

После изменения импорт и диагностика при одинаковых имени, производителе, типе, разрешённых характеристиках и конфигурации должны возвращать одинаковые кандидаты, распознанные значения и конфликты. Применение значения к строке остаётся отдельной политикой импорта: одинаковое распознавание не означает перезапись ручных данных.

## 1. Вынести общую композицию в модуль Recognition

Создать общий сервис распознавания действующей конфигурации (например, ICatalogEffectiveRecognitionService). Перенести в него выполнение и объединение baseline + active rule sets из CatalogImportRecognitionEnrichmentService, включая проверки области, нормализацию и разрешение конфликтов. Использовать существующие исполнители правил и базовый движок; не создавать второй алгоритм рядом с первым.

Сервис принимает независимый от импорта запрос: имя, производитель (идентификатор и необходимые нормализации данные), тип товара, допустимые определения характеристик и контекст запуска. Он не принимает CatalogImportRow, workbook analysis или JSON строки. Возвращает общий результат распознавания и использованные версии активных правил. Не пишет feedback, товары или обучающие примеры.

Enrichment вызывает общий сервис, затем по прежним правилам решает, что заполнить, что оставить предложением и какие ошибки/предупреждения добавить. Сохранить порог уверенности, обработку конфликтов, некорректных Excel-значений и ручных исправлений. Не менять приоритеты источников под видом переноса кода.

## 2. Сохранить единый контекст запуска

Сохранить существующую фиксацию active rule sets в начале анализа. Один анализ, в том числе смешанных типов, использует один контекст; переключение версии во время обработки не меняет правила для оставшихся строк. Новый запуск подхватывает новое состояние.

В контексте лениво сохранять прочитанные профили и словарь так, чтобы один и тот же источник не перечитывался с иным содержимым для следующих строк. Если существующий lifetime уже даёт такую гарантию, переиспользовать его и описать границы. Не объявлять раздельные чтения атомарным снимком всей БД. Не вводить новую таблицу запусков или историческое версионирование всех справочников на этом этапе.

## 3. Подключить диагностическую страницу целиком

Добавить необязательный ManufacturerId в контракт preview, query, контроллер, frontend API и типы. На существующей странице распознавания добавить выбор производителя из существующего справочника. При заданных производителе и типе диагностика по умолчанию использует тот же общий сервис, что импорт.

Показать выбранную область и реально использованную версию активных правил либо отсутствие активной версии. Без производителя или типа сохранить доступную общую диагностику, но явно обозначить, что проверка правил конкретной области неполна. Не выбирать произвольного производителя и не показывать общий результат как точное воспроизведение импорта.

Старые запросы без ManufacturerId должны оставаться допустимыми. Ошибка загрузки/исполнения активной версии должна быть видимой; не откатываться молча к baseline. Согласовать доменные ошибки, HTTP-ответ и отображение на странице.

Если отдельный baseline-preview полезен существующим потребителям, сохранить его как явно обозначенный режим. Для обычной проверки с полной областью использовать действующую конфигурацию. Не добавлять экспериментальный workflow без необходимости.

## 4. Согласовать объяснение импорта с результатом

Проследить CatalogImportRecognitionShadowService и CatalogImportProductNameExplanationService. Объяснения характеристик и их конфликты должны строиться из того же результата, который использовался при enrichment, включая активные правила. Передавать уже рассчитанный результат, где возможно, вместо повторного распознавания с другим контекстом.

Проверить первый анализ, повторный анализ с ручными значениями и смешанные типы. Отдельную диагностику производителя и назначения типа сохранить: это другие стадии. Не показывать два противоречащих набора выводов по характеристикам как один результат. Если baseline shadow остаётся для сравнения, явно отделить его от объяснения фактического решения.

## Проверки в составе реализации

- Правило существует только в активной версии: оно одинаково видно в preview и import.
- Baseline и активное правило противоречат: оба пути одинаково показывают конфликт.
- Нет активной версии: действуют прежние базовые правила.
- Нет производителя: ограничение области показано явно, старый запрос не ломается.
- Переключение active rule set в середине анализа не меняет оставшиеся строки; следующий анализ использует новую версию.
- Ручные исправления и явные значения Excel сохраняются; распознанное предложение не становится принудительной перезаписью.
- Объяснение соответствует реальному результату в первом/повторном анализе и смешанном пакете.
- Проверить сборку API, целевые проверки импорта и frontend typecheck/build по принятым командам проекта. Не выдавать незапущенные проверки за успешные.

## Границы

Не менять фоновое обучение, eligibility, отзыв TrainingExamples, экспорт датасетов, генерацию черновиков и активацию версий. Не объединять и не удалять таблицы. Не добавлять новый экран обучения. Следующий отдельный этап — единые правила подтверждения, использования и отзыва обучающих данных.

## Итог

Вернуть внесённые изменения, фактические проверки и короткий пользовательский сценарий: выбрать производителя и тип, ввести имя, увидеть тот же результат, который использует импорт. Обновить карту архитектуры по реализации. Не присылать код для ручной вставки и не выполнять следующие этапы автоматически.
