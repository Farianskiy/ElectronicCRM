# Реализация: отделить накопление знаний от применения импорта

Это текущее задание реализатору. Оно заменяет обязательный тестовый этап из implementer-task-01.md и соответствующий порядок в первоначальном аудите. Нужно внести изменения в проект и проверить их, а не прислать предлагаемый код. Не останавливаться после плана или исходных проверок.

## Результат для пользователя

Применение импорта заканчивается после сохранения товаров и подтверждённой обратной связи. Накопление кандидатов и подготовка предложений словаря выполняются самостоятельно, продолжаются после перезапуска приложения и не требуют нового импорта. Неподходящие записи не блокируют подходящие записи дальше в очереди.

Сейчас CatalogImportBatchApplier после commit ожидает AggregateAsync и PromoteEligibleAsync. Они читают общие очереди. Удалить эту зависимость запроса импорта от обработки знаний.

## 1. Оставить импорту его работу

В CatalogImportBatchApplier сохранить существующую транзакцию записи товаров, аудита, статуса пакета и финализации feedback. Убрать вызовы TryAggregateRecognitionCandidatesAfterCommitAsync / TryPromoteRecognitionCandidatesAfterCommitAsync и соответствующие зависимости и логи из applier. Возвращать результат после успешного commit.

Не удалять финализацию feedback: именно сохранённый finalized training-eligible feedback будет долговечным входом для самостоятельной обработки. Не запускать её через Task.Run, таймер запроса или очередь только в памяти.

## 2. Добавить самостоятельную обработку знаний

В инфраструктуре добавить CatalogRecognitionLearningHostedService и настройки Enabled, PollInterval, BatchSize. Использовать существующий подход регистрации фоновых сервисов; ориентир — CatalogImportCleanupHostedService. В штатной конфигурации обработка включена, интервал по умолчанию 30 секунд, размер страницы 500. Проверять настройки при запуске.

Обработчик при старте и затем периодически:

1. Берёт сохранённый finalized training-eligible feedback.
2. Накапливает candidates/evidence существующим алгоритмом.
3. Обрабатывает кандидатов для подготовки предложений словаря существующей политикой.
4. Завершает проход; при ошибке записывает причину и повторяет работу в следующем цикле.

После сбоя сохранения не продолжать следующий этап на повреждённом отслеживаемом состоянии DbContext. Использовать новые DI scopes для независимых единиц работы. Соблюдать остановку приложения через CancellationToken.

Не создавать новую таблицу очереди: вход уже хранится в feedback, а evidence показывает успешную агрегацию. Не вводить брокер, микросервис или универсальный workflow.

## 3. Исправить продвижение обеих очередей

Изменить контракты reader/repository и обработчиков так, чтобы один проход последовательно обходил страницы, а не перечитывал первые 500 записей.

Для feedback использовать устойчивую сортировку FinalizedAtUtc + Id и курсор страницы. Продвигаться по просмотренным записям, включая deferred. Не применять offset к выборке, которая уменьшается после создания evidence. Сохранить порядок обработки Corrected перед Accepted/Rejected, поскольку исправления создают кандидатов.

Для accumulating candidates тоже обеспечить полный постраничный обход: неготовые первые кандидаты не должны скрывать готовые дальше. Использовать стабильный ключ обхода, не изменяемые счётчики в качестве единственного курсора.

Проход должен иметь конечную границу или бюджет работы и сохранять продвижение между своими итерациями. Непрерывное поступление данных не должно мешать остановке. В следующем полном проходе повторно рассматривать deferred: подходящий кандидат мог появиться позже. Не маркировать deferred как навсегда обработанные.

Курсор обхода может жить в обработчике: после рестарта допустим повторный обход, потому что feedback долговечен, а уже созданные evidence дедуплицируются. Сохранять уникальные ограничения CandidateKey и FeedbackId.

## 4. Конкуренция и авторство

Обеспечить единственного активного обработчика для общей БД при нескольких экземплярах API. Использовать PostgreSQL advisory lock с корректным освобождением и временем жизни соединения; локальный SemaphoreSlim недостаточен. Не держать одну транзакцию на весь объём очереди. Второй экземпляр пропускает проход, если блокировка занята.

Проверить авторство создаваемых предложений. Сейчас promotion получает пользователя, применившего последний импорт, хотя читает общую очередь. Фоновый процесс не должен притворяться этим пользователем. Использовать существующее представление системного действия, если оно есть. Если схема требует реального пользователя, явно передавать происхождение от подтверждённого feedback, породившего кандидата, и документировать выбранное правило. Не создавать фиктивную учётную запись и не использовать Guid.Empty. Если данных для требуемого авторства недостаточно, выдавать диагностируемую причину отсрочки, не останавливая остальную очередь.

## 5. Наблюдаемость

Добавить структурированные логи начала/завершения прохода, количества просмотренных feedback и candidates, добавленных evidence и suggestions, deferred и ошибок. Различать успешное применение импорта и результат фоновой обработки. Не называть обработку успешной, если она завершилась ошибкой. На этом этапе отдельная страница мониторинга и таблица метрик не нужны.

## Границы этого изменения

Сохранить существующие распознавание, автозаполнение, ручные исправления, подтверждение/отзыв TrainingExamples, генерацию черновиков и переключение версий. Не объединять таблицы и не менять политику допуска данных к обучению. Задача выделяет самостоятельный жизненный цикл накопления знаний; унификация движка распознавания будет следующим отдельным изменением.

## Проверка результата в составе реализации

Проверить конкретные гарантии:

- Применение импорта сохраняет товары и feedback без выполнения aggregation/promotion внутри запроса.
- Фоновый процесс обрабатывает уже существующий feedback без нового импорта, в том числе после своего перезапуска.
- Более 500 deferred не блокируют подходящую запись за ними; проверить обе очереди.
- Повторная обработка не удваивает evidence и счётчики; две копии обработчика не обрабатывают очередь одновременно.
- Ошибка фонового шага не отменяет применённый импорт; следующий цикл продолжает работу с чистым контекстом.
- Существующие проверки ручных значений и конфликтов импорта проходят.

Добавить только проверки изменённого поведения. Исходные проблемы тестовой инфраструктуры исправлять минимально, если это необходимо для целевых запусков; не превращать их в отдельный масштабный рефакторинг. Использовать изолированную тестовую БД, не рабочую БД и не пользовательский dump. Внешние блокировки сообщать точно, не выдавая незапущенную проверку за успешную.

Реальные изменения файлов, краткое описание нового цикла, настройки фоновой обработки, результаты выполненных проверок и оставшиеся ограничения. Не возвращать сотни строк кода для ручной вставки. Обновить архитектурную карту по фактически реализованному поведению. Не выполнять следующие этапы автоматически.
