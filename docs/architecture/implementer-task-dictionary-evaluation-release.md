# Этап 6. Проверяемый выпуск словарных предложений из обучения

Реализовать непосредственно в проекте. Сохранить результаты этапов 1–5 и незакоммиченные изменения. Не ограничиваться аудитом или тестами. Сначала прочитать архитектурную карту и `learning-evaluation-release-implementation.md`, затем проверить актуальный код: документация не заменяет проверку реализации.

## 1. Результат и границы

Замкнуть вторую ветку обучения:

Feedback → кандидат → словарное предложение → сравнительная оценка → явное одобрение → словарный термин → последующий импорт/preview.

Сейчас одобрение предложения проверяет основания через EvidenceRevision, но не проверяет изменение результата распознавания. После реализации предложение из обучения нельзя выпустить без актуального отчёта о его влиянии.

Этап охватывает предложения с `IsGeneratedFromRecognitionLearning`, выпускаемые как Characteristic в полной области «производитель + тип товара». Проверка нужна по происхождению предложения, а не только по присланному Kind: смена Kind, области или других полей не должна позволять обход. Неподдерживаемую форму решения для такого предложения отклонять с понятной причиной; не оставлять старый путь одобрения как fallback.

Ручные предложения других источников, Manufacturer/ProductType/SearchToken, глобальные термины, прямое администрирование словаря и исправление уже выпущенных терминов не объединять с этим выпуском. Сохранить их существующие проверки и явно описать эту оставшуюся границу. Любая разрешённая запись в словарь по-прежнему должна делать зависимые отчёты устаревшими. Не объявлять весь словарь версионированным или все пути изменения распознавания закрытыми.

Не добавлять автоматическое одобрение, очередь, микросервис, универсальный workflow или вторую систему активных правил. Не выполнять последующие этапы общего интерфейса и сроков хранения.

## 2. Переиспользовать сравнительную оценку

Опорные компоненты: RecognitionComparisonEvaluator, EvaluationJson, RecognitionEvaluationCapture/Service/Reports, CatalogEffectiveRecognitionService, CatalogRecognitionRunContext, существующая политика этапа 5, ApproveCatalogAssistantDictionarySuggestionCommandHandler, CatalogDictionarySuggestionApprovalDecision, RecognitionMutationGate и LearningProvenanceService.

Текущий EvaluationInput рассчитан на две версии правил с одинаковым baseline. Минимально расширить общий механизм до двух явно заданных конфигураций распознавания. Не копировать evaluator, классификатор исходов, нормализацию, метрики, правила допуска или UI отчёта в отдельную реализацию словаря.

Две стороны словарной оценки:

- текущие словарь/профили/схема + действующая версия правил;
- тот же набор, дополненный ровно одним термином из окончательного решения одобрения, + та же действующая версия правил.

Не отключать активные правила на время сравнения. Кандидатный термин может вызвать конфликт с ними — это часть измеряемого результата. Термин для симуляции не сохранять в рабочий словарь и не подмешивать в кеш другого запроса. Ручные значения импортированных товаров не использовать вместо ожидаемой разметки и не перезаписывать.

Симулируемый термин строить тем же доменным путём, что термин при одобрении: нормализация фразы, область, Kind, TargetCode, TargetValue, Priority и проверка дубликатов должны совпадать. Отпечаток решения не должен случайно меняться из-за заново сгенерированного ID/времени временного термина.

Все редактируемые поля окончательного решения включить в снимок. Изменение любого значимого поля формы после оценки требует новой оценки. Сервер проверяет это независимо от UI; EvidenceRevision и ReportId не заменяют сравнение содержимого решения.

## 3. Хранение и совместимость

Сохранить неизменяемый отчёт с областью, автором, временем, типом оцениваемого изменения, SuggestionId/CandidateId, окончательным решением, EvidenceRevision, конфигурациями обеих сторон, разметкой/источниками, политикой, отпечатками, результатами и причинами допуска.

Предпочесть развитие существующего хранения отчётов, но не создавать фиктивную RuleSetVersion или пакет импорта для словарного отчёта. Если обязательные связи RuleSetReport мешают, выбрать минимальное совместимое решение и документировать его: расширение с явными ограничениями видов отчётов либо специализированное хранение словарных снимков, использующее общий механизм оценки. Отдельная таблица при обоснованной модели допустима; параллельный вычислительный механизм и дублирование истории одобрения — нет. Исключить неоднозначные сочетания типа отчёта и ссылок ограничениями БД.

Словарная оценка не требует пакета импорта. Для выпуска RuleSetVersion прежнее требование пакета и все его проверки сохраняются.

Старые RuleSetReport остаются читаемыми. Поддерживаемые снимки этапа 5 должны по-прежнему воспроизводиться; при изменении формата использовать явную версию и адаптер, а не молча другую семантику. Разрешение на новый выпуск всё равно требует текущих проверок. Одобрения прошлых лет не переписывать и задним числом не объявлять оценёнными.

Повтор словарного отчёта использует только сохранённые зависимости распознавания. Чтение живых данных допустимо для авторизации и загрузки самого отчёта, но не для воспроизведения recognizer. Исторические исключённые источники показывать как исторические; повтор не даёт разрешения на одобрение.

## 4. Контроль без известных учебных пересечений

Переиспользовать выборку активных собственных TrainingExamples с доступным не исключённым Feedback. Единица, дедупликация, конфликт разметки, нормализация значений и знаменатели — как в этапе 5.

Исключить из контрольной группы все нормализованные имена, которые встречаются:

- в сохранённых основаниях оцениваемого кандидата/предложения, включая записи, ранее участвовавшие, но позднее исключённые;
- в evidence действующей версии правил всех трёх видов, включая checked.

Проверять пересечение по имени внутри области, по всем характеристикам, а не только по ID или целевой характеристике. Если фактическая модель хранит несколько видов оснований предложения, перечислить и учесть их. При неполных/потерянных обязательных основаниях не выдавать готовность молча. Чужие примеры и разметку через отчёт не раскрывать: для исключения пересечений использовать необходимые внутренние сведения без вывода чужих строк.

`IsEvaluationOnly` сейчас резервирует пример для контроля правил, но не исключает его Feedback из фонового обучения словаря. Не считать этот флаг доказательством независимости словарного контроля и не менять его смысл незаметно. Для этой оценки решающим является отсутствие известных пересечений с основаниями. Существующий интерфейс назначения примеров сохранить, пояснения уточнить.

Чётко писать «Контроль без известных пересечений с основаниями», не обещать полной статистической независимости от исторического словаря. Недостаточный контроль — блокирующее состояние с пояснением, какие новые подтверждения нужны. Не использовать учебные имена вместо контроля.

## 5. Общая политика допуска

Использовать общие серверные метрики и настройки этапа 5: минимальные размеры контроля и число исправлений, ноль регрессий, отсутствие роста неправильных значений/конфликтов, запрет противоречивой разметки и ошибок вычисления. Оценивать все размеченные характеристики контрольных имён, а не только TargetCode предложения.

Достаточные учебные основания кандидата и актуальный EvidenceRevision остаются отдельными обязательными условиями. Улучшение на контроле не компенсирует недостоверные основания. Проверка оснований не подменяет оценку качества.

Состояния и причины готовности переиспользовать из общего контракта. Клиент не присылает доверенный ready-флаг, метрики или пороги. Без измеримого улучшения обычное одобрение запрещено. Не вводить force/skipEvaluation и не разрешать дубль существующего термина под видом выпуска.

## 6. Атомарное одобрение и актуальность

Расширить существующее действие одобрения ссылкой на собственный отчёт и явным подтверждением решения. Для предложений из обучения отсутствие отчёта блокирует старый endpoint, даже при правильном EvidenceRevision. Для уже обработанного предложения повторный запрос не создаёт ещё один термин или новое одобрение.

Порядок: общий gate → свежая транзакция → авторизация и чтения → проверка актуальности/готовности → сохранение термина, решения предложения, состояния кандидата и связи с использованным отчётом → единый commit → освобождение gate. Не брать gate повторно из вложенного сервиса. Не считать один SaveChanges достаточной защитой всего предшествующего чтения без транзакционной границы.

Под защитой проверить автора отчёта, доступ к предложению, Pending, происхождение, область, финальное решение, отсутствие дубликата термина, EvidenceRevision и достаточность оснований; текущие словарь/профили/схему/активные правила, состав допустимого контроля и политику.

Проверить конкурирующие пути, включая отклонение предложения, обновление оснований, агрегацию/promotion, отзыв/исключение, прямую запись словаря, изменение профиля/схемы и переключение правил. Триггеры этапа 5 не покрывают автоматически любые новые таблицы/записи — при необходимости расширить защиту и документировать порядок. Две конкурентные оценки не обязаны блокировать друг друга; две активации конфликтующих изменений не должны обе пройти по одному старому состоянию.

Устаревший допуск возвращает 409 со стабильным кодом и предложением повторить оценку. При отказе не оставлять термин, Approved-предложение или частично изменённого кандидата. Новый термин должен устаревать ранее выданные допуски выпуска правил в затронутой области. Новый запуск preview/импорта использует выпущенный термин; закреплённый контекст старого запуска сохраняет уже загруженный словарь согласно существующей семантике кеша.

## 7. Права, лимиты и интерфейс

В create/read/replay/readiness/approve проверять активность пользователя и эффективное право DictionariesManage с overrides, плюс существующие ограничения доступа к предложению. Текущую проверку роли через CanManageProductSynonyms сверить с общим механизмом разрешений; не оставить расхождение, позволяющее обход override. Глобальность учебных кандидатов не означает публичность чужих контрольных примеров. Отчёт и его строки доступны автору при текущих разрешениях.

Переиспользовать ограничения времени, размера JSON, входной выборки и серверную пагинацию. Превышение лимита, повреждённая конфигурация или timeout — явная ошибка без частичного успешного отчёта/одобрения. Не удерживать общий gate на всё время сравнительного расчёта; согласованный снимок и свежая проверка при одобрении обязательны.

Расширить существующую страницу словарных предложений:

1. Отредактировать окончательное решение.
2. Запустить «Оценить влияние».
3. Увидеть область и решение, контроль, исправления, регрессии, учебные пересечения, достаточность оснований и причины запрета.
4. Явно одобрить именно проверенное решение.

Использовать общий компонент отчёта с подходящими подписями для словаря/правил. При редактировании формы старый допуск визуально сбрасывается; сервер всё равно проверяет поля. После одобрения обновлять список, статус и происхождение без перезагрузки; ошибка не показывает успех. Сохранить просмотр и исторический повтор отчёта после одобрения. Добавить реальную связь использованного отчёта в просмотр происхождения, без выдуманных связей для старой истории.

## 8. Приёмочные сценарии

- Сравнение без сохранения временного термина; обе стороны используют одинаковые активные правила, настоящий baseline и общий recognizer. Выпуск создаёт термин с теми же значимыми полями, которые оценивались.
- Улучшение без регрессий допускает одобрение; отсутствие улучшения, регрессия/конфликт по любой размеченной характеристике, недостаточный контроль и конфликт разметки блокируют прямой HTTP-вызов.
- Учебные имена кандидата и активных literal/integer/multi-integer правил, включая checked и исторические основания, не попадают в контроль. Дубли не увеличивают знаменатель.
- Замена Phrase/TargetValue/Priority/TargetCode/области/Kind, чужого ReportId, SuggestionId или EvidenceRevision не позволяет использовать прежний допуск. Старый запрос без отчёта не обходит защиту предложения из обучения.
- Изменение словаря, профиля, схемы, правил, политики, состава подтверждений и оснований делает допуск устаревшим; повтор старого снимка сохраняет результаты.
- Конкурентные одобрение/исключение, одобрение/отклонение, два одобрения одного предложения и два влияющих друг на друга выпуска дают согласованный результат без частичных записей. Проверить gate до снимка транзакции, а не только уникальный индекс после ошибки.
- Чужой, заблокированный пользователь и пользователь с запрещающим permission override не читают контроль и не одобряют предложение. Подмена report kind не даёт применить словарный отчёт для RuleSetSwitcher и наоборот.
- После одобрения новый preview и импорт видят термин; ранее начатый контекст с загруженным словарём сохраняет снимок. Зависимый отчёт правил становится устаревшим.
- Исторические отчёты этапа 5 воспроизводятся; текущий выпуск правил, его обязательный пакет и явное отключение до baseline работают как прежде.
- Лимиты/timeout не сохраняют частичный отчёт. Cleanup импорта не удаляет самостоятельный словарный отчёт.

Использовать временную PostgreSQL со штатными миграциями и реальный HTTP для проверки запрета одобрения. Запустить целевые backend-тесты, сборки API/frontend, TypeScript и ESLint. По возможности пройти браузерный путь; отдельно перечислить незапущенные проверки. Не подменять результат числом тестов: описать проверенные пользовательские сценарии.

## 9. Работа с базой и сдача

Рабочую базу и пользовательские dump не использовать. Не запускать API с рабочей строкой подключения для проверки сборки: Program.cs автоматически вызывает MigrateAsync и seeder при старте. Миграции проверять на изолированной базе; к рабочей базе их не применять в рамках этого задания.

Обновить `docs/architecture/import-learning-audit.md` и создать `docs/architecture/dictionary-evaluation-release-implementation.md`: модель снимка, совместимость, границы контроля/прав, атомарность, лимиты, результаты проверок, оставшиеся ручные пути изменения словаря и порядок развёртывания с учётом автоматических миграций при запуске API. Явно указать необходимость согласованного обновления экземпляров при изменении gate/триггеров.

Результат этапа — обе ветки обучения используют один принцип «сначала измерить влияние, затем явно выпустить», сохраняя свои доменные объекты. Общий экран полного цикла и политика хранения остаются следующими самостоятельными заданиями.
